## 1. チェックポイント同一性の検証（レビュー §4 対応）

### 1.1 動機

レビューは、§0で報告した「ベースVideo2Worldチェックポイントがキャッシュから消えて
再取得ルートに切り替えた」というドリフトが、round 2 で観測された run 間変動
(成功率70%↔60%↔58%、PR 55↔4等)の**共通原因である可能性を排除できていない**と指摘した。

### 1.2 方法・結果

HuggingFace キャッシュ (`HF_HOME=/mnt/data/bilgehan.sakai/cosmos-policy/cache/huggingface`)
を直接調査した。

**ポリシー本体チェックポイント** (`nvidia/Cosmos-Policy-RoboCasa-Predict2-2B`):
- blob ハッシュ `ed4b991612b0d75e5e633fb2ca821e54c66a3b89973eb361e6ca50ba4984506f`
  （3,913,017,345 bytes）のみが存在し、**キャッシュされたのは 2026-04-01 23:00**。
- スナップショットコミットは `4b2a04c80d97202f86127ebec80461e8016ec1dc` の1つのみ。
- これは元の50-episode run（features.npz生成、2026-06-30）よりも3ヶ月近く前から
  存在しており、以後 T8・T6・extended-step・pad_attn_verify を含む本セッションの
  全実行時点でも同一のまま変化していない。
- 追加のblob (`d7f067f0...`, 1.24GB, キャッシュ日2026-04-25) は
  `robocasa_t5_embeddings.pkl` または `robocasa_dataset_statistics.json` に対応する
  サイズであり、ポリシー本体の重みではない。

**ベース Video2World チェックポイント** (`nvidia/Cosmos-Predict2-2B-Video2World/model-480p-16fps.pt`):
- こちらは実際に 2026-07-06（本セッション中）に再ダウンロードされている
  （§0 で報告した通り）。スナップショットは `f50c09f5d8ab133a90cac3f4886a6471e9ba3f18` の1つのみ。

しかし `model_loader.py::load_model_from_checkpoint` のコードを確認すると:

```python
if s3_checkpoint_dir:
    config.checkpoint.load_path = str(s3_checkpoint_dir)
```

という行があり、**実験config内で宣言されている `load_path`（ベースVideo2World
チェックポイントを指す）は、推論時に必ず `s3_checkpoint_dir`（= 実際に指定した
`ckpt_path`、本解析では常に `nvidia/Cosmos-Policy-RoboCasa-Predict2-2B`）で
上書きされる**ことが確認できた。つまり、**ベースVideo2Worldチェックポイントの重みは
推論経路では一度も読み込まれない**。config内の`load_path`宣言(base checkpointを指す)は
上書きされて無効化される。ベースチェックポイントが実際に使われるのは
`vae_pth`(トークナイザ、tokenizer.pth)としてのみであり、これは別ファイル・別の
安定した凍結アーティファクトである。

### 1.3 結論

**ポリシーの DiT 重みは、全ての解析(元の50ep run含む)で単一の同一チェックポイント
blob により100%決定されている**。ベースVideo2Worldチェックポイントの再ダウンロード
イベントはDiT重みに一切影響しない。したがって、**チェックポイントdriftはround 2で
観測された run 間変動の原因ではあり得ない**——原因は別の場所にある（§2 で特定）。

## 2. T6「run間変動」の根本原因訂正 — 実際にはPCA前処理の選択だった（v2 §4 の重大な訂正）

### 2.1 v2 §4 の主張（訂正対象）

v2 は、第1回レポートの「旧(Global PCA+Ridge, 成功率70%)」と「新(fold-PCA+LR, 成功率60%)」
の比較について、`probe_stats.json`(成功率0.70)と`feature_stats.json`/`features.npz`
(成功率0.60)の成功率不一致を根拠に、「実際には異なるrun(rollout)から得られた別々の
特徴量データだった」と結論した。

### 2.2 この結論は誤りだった

`linear_probe.py`（第1回レポートの"旧"パイプラインの実コード）のヘッダを確認すると、
実行例は次の通り:

```
python -m cosmos_policy.experiments.robot.robocasa.analysis.linear_probe \
    --feat_npz cosmos_policy/experiments/robot/robocasa/analysis/results/action_features/features.npz \
    --actions_npz cosmos_policy/experiments/robot/robocasa/analysis/results/action_denoising/step_actions.npz \
    --out_dir cosmos_policy/experiments/robot/robocasa/analysis/results/action_probe \
    --task_name PnPCounterToCab \
    --success_rate 0.70
```

**"旧"パイプラインは現在の`features.npz`と全く同じファイルを読むよう設計されている**。
`--success_rate`はプロットのタイトル注釈にのみ使われる**手動指定のCLI引数**であり
(`parser.add_argument("--success_rate", type=float, default=0.70)`)、データから
自動算出される値ではない。すなわち`probe_stats.json`内の`success_rate: 0.70`は、
**実データを反映しない古いデフォルト値の書き残し**であり、"別runの証拠"ではなかった。

これを実証するため、`linear_probe.py`を現在の`features.npz`/`step_actions.npz`に
対してそのまま再実行した:

```
python -m cosmos_policy.experiments.robot.robocasa.analysis.linear_probe \
    --feat_npz .../action_features/features.npz --actions_npz .../action_denoising/step_actions.npz \
    --out_dir /tmp/.../v1_rerun --task_name PnPCounterToCab --success_rate 0.70
```

結果 (progress_3, k=4):

| Layer | 再実行した実際のv1コード | 元の`probe_stats.json`の値 | 差 |
|---|---|---|---|
| Blk-4  | 0.44 | 0.435 | ≈0 |
| Blk-9  | 0.44 | 0.438 | ≈0 |
| Blk-13 | 0.57 | 0.569 | ≈0 |

**同一の単一`features.npz`から、実際のv1コードで元の報告値をほぼ完全に再現できた**
——つまり「別run」という前提そのものが誤りであり、実際は**常に同一の単一データセット**
だった。

### 2.3 では真の原因は何か — 2要因アブレーションで確定

v2 §4の`t6_decompose_confound.py`が計算した「旧手法参照値」(Global PCA n=50+Ridge:
Blk-4=0.594, Blk-9=0.638, Blk-13=0.645)は、上記の実際のv1出力(0.44, 0.44, 0.57)と
7〜21pp食い違う。この2つの実装を1行ずつ比較すると、**2つの前処理の相違点**が見つかった:

- **要因A (PCA入力のスケーリング)**: v1の`pca_project`は生の2048次元特徴量を
  **中心化のみ**(`X_c = X - X.mean()`)してからSVDする。`t6_decompose_confound.py`の
  `pca_global_leaked_fit`は**標準化(z-score)してから**(`X_s = (X-mu)/std`)SVDする。
- **要因B (Ridge直前のスケーリング)**: v1の`ridge_probe`はPCA後の50次元スコアを
  **訓練foldで再標準化**してからridgeに渡す。`t6_decompose_confound.py`の
  `ridge_fit_predict`はPCAスコアをそのまま渡す(再標準化なし)。

この2要因を独立に切り替える2×2アブレーションを`features.npz`に対して直接実行した
(`cosmos_policy/experiments/robot/robocasa/analysis/t6_pca_scaling_ablation.py`,
progress_3, k=4, n_comp=50, 全7層でLOEO再計算):

| Layer | A=中心化,B=fold再標準化<br>(v1を完全再現) | A=標準化,B=なし<br>(t6_decompose の参照セル) | A=中心化,B=なし | A=標準化,B=fold再標準化 |
|---|---|---|---|---|
| Blk-0  | 0.5482 | 0.5544 | 0.5486 | 0.5544 |
| Blk-4  | **0.4352** | **0.5939** | 0.4352 | 0.5939 |
| Blk-9  | **0.4376** | **0.6378** | 0.4376 | 0.6378 |
| Blk-13 | **0.5689** | **0.6451** | 0.5689 | 0.6451 |
| Blk-18 | 0.7028 | 0.7053 | 0.7028 | 0.7053 |
| Blk-22 | 0.7237 | 0.7196 | 0.7237 | 0.7208 |
| Blk-27 | 0.7224 | 0.7324 | 0.7224 | 0.7324 |

決定的な観察:
1. **「A=中心化,B=fold再標準化」列はprobe_stats.jsonの元の値(0.435, 0.438, 0.569)と
   小数点以下まで一致**する——これがv1の真の挙動の完全な再現であることの確証。
2. **「A=標準化,B=なし」列はt6_decompose_confound.pyの「旧手法参照値」(0.594, 0.638, 0.645)
   と一致**する——これがt6_decompose側の実装がしていたことの確証。
3. **要因B(Ridge直前の再標準化の有無)は結果に一切影響しない**
   (「A=中心化,B=fold再標準化」列と「A=中心化,B=なし」列が完全に同一の数値)。
4. **要因A(PCA前に標準化するか中心化のみか)だけで、全ての差が説明できる**
   (Blk-4: +15.9pp, Blk-9: +20.0pp, Blk-13: +7.6pp — v2報告の"+11〜21pp"にほぼ一致)。

### 2.4 なぜPCA前の標準化がこれほど精度を変えるのか

`feature_stats.json`が示す通り、各層の生特徴量の分散は層間で大きく異なる
(Blk-0:1.9〜Blk-27:210141)。同一層内でも2048次元間の分散はおそらく大きく偏っている。
**標準化せずにPCAすると、上位主成分は「分散が大きい少数の次元」に支配され**、
それが必ずしも分類に有用な方向とは限らない。**標準化してからPCAすると、全次元が
等しく寄与するため、分類に有用な方向がより多く上位主成分に残る**——これは
PCA前処理における非常によく知られた"whitening vs non-whitening"の効果であり、
run やロールアウトの違いとは無関係の、純粋に決定論的な前処理選択の結果である。

### 2.5 訂正した結論

- **v2 §4の「旧/新プローブ比較は異なるrunだった」という結論は誤りであり撤回する**。
  実際には**単一の同一run・同一features.npz**の中で、PCA前処理(標準化 vs 中心化)
  という1つの選択が+7〜20ppの差の**全量**を説明する。
- レビューが指摘した「リーク除去は通常精度を下げるはずなのに中間層は逆に上がった」
  という逆説は、**"リーク除去"や"分類器変更"が原因ではなく、"PCA前の標準化"という
  第4の(当初分解されていなかった)要因が原因**だったことになる。標準化してからPCAすると
  Ridge/LR・n_comp30/50によらず一貫して高くなる(§4.2表の全セルで確認済み)。
- v2の「run差が支配的要因」という説明は誤りだったが、レビューが要求した
  「厳密な要因分解をせよ」という指摘は完全に正しく、その結果、**当初考えられていた
  よりもさらに単純でありふれた原因（1行のPCA前処理の選択）**にたどり着いた。
- `success_rate`フィールドをrunの識別子として使うのは危険である
  (`linear_probe.py`のようにCLI引数のデフォルト値がそのまま保存されるケースがある)。
  今後run同一性を確認する際は、`run_manifest.json`の`sha256`フィンガープリントか、
  `episode_labels`配列そのものの一致を確認すべきである(本レポートでは後者を用いて
  同一性を直接確認した: `features.npz`の`episode_labels`は0〜49の50エピソード、
  `linear_probe.py`の実行ログも同じ`episodes=[0...49]`を表示している)。

## 3. PRのepisode数依存性 — 既存の良い50ep features.npzによる単離（レビュー §2(b) 対応）

### 3.1 方法

レビューは「25ep runとの比較は別runとの比較であり、episode数の効果を単離するには
良い50ep `features.npz` を実際にepisode単位で縮約すべき」と指摘した。
`features.npz` には `episode_labels`（各callがどのepisode(0-49)由来かを示す配列）が
既に保存されていることを確認し、これを使って **run を一切またがない** episode単位
サブサンプリング学習曲線を作成した
(`cosmos_policy/experiments/robot/robocasa/analysis/pr_episode_curve.py`)。
episode数 n∈{2,3,5,10,15,20,25,30,40,50} それぞれについて、50エピソードから n個を
非復元抽出し(n<50は30回リサンプル、n=50は全データそのもの)、該当callの特徴量で
PR(Participation Ratio)を計算した。

### 3.2 結果

k=0, Blk-4のPR学習曲線(全7層・全5ステップで同様の傾向、詳細値は`pr_episode_curve.json`):

| n_episodes | 2 | 3 | 5 | 10 | 15 | 20 | 25 | 30 | 40 | 50(全データ) |
|---|---|---|---|---|---|---|---|---|---|---|
| 平均PR | 25.2 | 30.8 | 39.3 | 46.8 | 50.2 | 52.3 | 53.4 | 54.1 | 55.2 | **55.9** |
| 95%CI | [18.2,31.5] | [24.9,37.9] | [33.7,44.1] | [41.1,50.9] | [48.1,52.2] | [50.7,53.9] | [52.5,54.6] | [53.1,55.0] | [54.5,55.7] | (全データ) |

**滑らかで単調な飽和曲線**であり、n=50(全データ)でPR=55.89に達する——これは第1回
レポートが報告した「PR≈55.8」の値そのものである(同一データなので当然一致)。
**n=25の時点で既にCI=[52.5,54.6]まで収束しており、この良い50ep runの実データを
25エピソードに縮約しても、PRは3-4のような値には決して落ちない**。

### 3.3 決定的な反証: round 2の「episode数依存」説は不十分だった

round 2は「PR≈2-4(25ep, `extended_step_effrank_jb.py`) vs PR≈55(50ep, 元のrun)」の
差を「episode数の違い」で説明しようとした。しかし本節の結果は、**同一の良いrunの
実データを25エピソードに絞ってもPRは53付近(55からわずかな低下)にしかならない**
ことを示しており、round 2の「episode数依存」という説明では**この15倍規模の乖離を
到底説明できない**ことが確定した。§4でこの矛盾の真因を追跡する。

### 4.3 根本原因の特定: シード固定バグ（当初「未解明」としたが、その後の追加調査で完全に特定・実証済み）

**当初、キッチンレイアウト多様性・画像ピクセル多様性という2つの仮説を検証・否定した後、
根本原因は「未解明」と記録していた。その後さらに調査を進め、真因を特定した。**

`get_action()`(`cosmos_utils.py`)は`seed`引数を`model.generate_samples_from_batch(...,
seed=seed, ...)`に直接渡し、そこで`seed_g = torch.Generator(device=...); seed_g.manual_seed(seed)`
としてデノイジングの**初期ノイズ x_T のサンプリングそのもの**を制御する
(`text2world_model.py`)。ここで両スクリプトの`seed`引数の与え方を比較すると:

- `feature_analysis.py`(良いrun): `seed=cfg.seed + ep_idx + t` — **ほぼ全てのpolicy call
  で異なる値**(episode番号とタイムステップ番号の両方で変化)。
- `extended_step_effrank_jb.py`(§4.2以前のバージョン): `seed=cfg.seed` — **全てのpolicy
  callで完全に同一の固定値**。`t8_fixed_input_control.py`・`t8b_info_source_test.py`は
  それぞれ独自にcall毎/pair毎の変化するseedを使っており(後述、この2つは無関係と確認済み)、
  影響を受けるのは`extended_step_effrank_jb.py`のみだった。

すなわち`extended_step_effrank_jb.py`は、**全てのepisode・全てのcallにわたって、
デノイジングの初期ノイズ x_T を毎回ビット単位で完全に同一のテンソルに固定していた**。
これが真因であることを、シーン多様性を一切変えないクリーンな実験で実証した
(`cosmos_policy/experiments/robot/robocasa/analysis/confirm_seed_rootcause.py`):
1回の closed-loop ロールアウト
(12 episodes, N=352 calls)で観測プールを1度だけ収集し、**全く同一の観測集合**を
(A) 全callで固定seed(バグ再現)、(B) call毎に変化するseed(feature_analysis.py方式)
の2条件でモデルに通し、k=0のPRを比較した:

| Layer | 固定seed(バグ再現) | 変化するseed(良いrun方式) | 倍率 |
|---|---|---|---|
| Blk-0  | 1.27 | 7.93  | 6.2× |
| Blk-4  | 1.90 | **53.71** | 28.3× |
| Blk-9  | 2.91 | **54.23** | 18.6× |
| Blk-13 | 4.07 | **50.04** | 12.3× |
| Blk-18 | 9.10 | 14.15 | 1.6× |
| Blk-22 | 9.23 | 11.70 | 1.3× |
| Blk-27 | 2.72 | 2.78  | ~1.0× |

**シーン・観測は一切変えず(全く同一の352 call)、seedを変化させるだけでBlk-4/9/13の
PRは元の良いrunの値(≈53-56)にほぼ完全復元した**。これは完全な確証であり、
「キッチンレイアウト」「画像多様性」という当初の2仮説が正しく否定される一方で
見落としていた3つ目の要因——**初期ノイズのseed固定**——が唯一かつ十分な原因
だったことを示す。

**層による感度の違いも意味がある**: Blk-4/9/13(中間層)はseed変化に強く反応する
(12-28倍)一方、Blk-18/22(深層寄り)は僅かにしか反応せず(1.3-1.6倍)、Blk-27
(最深層)はほぼ無反応(1.0倍)。これは§5-7で確立した「深層は条件付け由来の情報に
強く依存し、初期ノイズの具体的な実現値にはあまり依存しない」という描像と完全に
整合する——中間層の表現は依然として「どの特定のノイズを引いたか」に強く紐づいており、
深層に進むほど条件付け由来の安定した信号に置き換わっていく。

**修正**: `extended_step_effrank_jb.py`の該当行を
`seed=cfg.seed` → `seed=cfg.seed + total_calls`(call毎に変化)に修正した。
`t8_fixed_input_control.py`(`call_seed = cfg.seed + pair_idx`、pair毎に変化)と
`t8b_info_source_test.py`(`call_seed = cfg.seed*1000 + call_seed_counter`、call毎に
変化)は元々この問題を抱えておらず、影響を受けていない。

### 4.4 崖 vs 滑らかの判定への影響、および修正版での再検証

**この発見は§4.2の「崖 vs 滑らか」の形状観察そのものにも疑いをかける**。
seed固定による多様性抑制の強さはσに依存する可能性が高い(σが大きい=ノイズが支配的な
段階ほど、"どの特定のノイズを引いたか"を固定することの影響が大きく、σが小さくなり
デノイジングが条件付け由来の信号を解決するにつれて影響は薄れるはずである)。
実際、§4.2の(バグ入り)データではPRがidx0(σ=80)で最低、中間σでピークを迎え、
その後低下するという形状を示していた——この「idx0が低い」という部分は、
seed固定の影響がσ=80で最大になることと整合するため、**§4.2で報告した崖→滑らか
の形状自体が、真の denoising ダイナミクスではなく seed固定バグのアーティファクトで
ある可能性が高い**。修正版スクリプトで再実行し、この節を更新する必要がある
(§4.5に結果を追記)。

**今後この系列のスクリプトで過去に生成されたPRデータ(修正前の`extended_step_results.json`,
25ep版・50ep版とも)は、絶対値・相対形状のいずれについても信頼できないものとして
扱い、引用しないこと**。

## 5. T8b: gripperプローブの情報源テスト（レビュー §3 対応）

### 5.1 動機

T8(v2 §3)は「条件付け(画像/proprio)の差し替えが action-token の内部特徴量
(feature-Δ最大0.20)を変化させる」ことを示したが、gripper出力自体の変化は
わずか(Δ=0.0018)であり、レビューは「これだけでは§3.Gの高精度gripperプローブ
(96-97%)が条件付けを読んでいることの証拠にはならない」と指摘した。要求された
テスト: 「gripper状態が異なる2つの観測の条件付けを入れ替えたとき、学習済み
gripperプローブの予測が差し替え先(source)を追従するか、元(base)のままか」。

### 5.2 方法

新規スクリプト `t8b_info_source_test.py` を実装した。まず通常のclosed-loop
ロールアウト(自身の行動で環境を実際に進める、15 episodes)を行い、各policy call
で(a) 実際にモデルに入力された観測、(b) action-token特徴量(k=0、baseline/未差し替え)、
(c) ラベル(後述)をキャッシュした(pool: 311-360 calls)。ラベルが異なる2つのcall
(i, j、異なるepisode由来)のペアを全て抽出し、call iの条件付け(proprio単独/画像単独/
全部)をcall jのもので差し替えて(iの乱数シードは固定)再度モデルに通し、
action-token特徴量を取得。**iとjの両方のepisodeのデータを除外して学習した
プローブ**でこの差し替え特徴量を分類し、予測がjの真のラベル(follows_source,
条件付け由来)に一致するかiの真のラベル(stays_base, 行動潜在由来)に一致するかを
判定した(2値ラベルなので必ずどちらか一方に分類される)。

**ラベル定義は2種類試した**:
1. `current_proprio`: 観測時点の生のproprio(`robot0_gripper_qpos`平均)から直接得られる
   「現在の真のgripper開閉状態」の中央値2値化。
2. `action_gripper`: 最終デノイジングステップでモデルが実際に出力したgripper次元
   (index 6)の32-stepチャンク平均の中央値2値化——これは §3.G/T8 の元の
   `gripper_2` プローブが実際に予測していたラベルと同じ定義である。

深層でも55-65%程度にしか到達しない**。これは、深層の高精度gripperプローブが
「入力proprioの単純な通過(パススルー)」では説明できないことを示す、

| Blk-13 | 0.417 | 0.250 | **0.667** |
| Blk-18 | 0.283 | 0.267 | **0.733** |
| Blk-22 | 0.383 | 0.217 | **0.767** |
| Blk-27 | 0.283 | 0.117 | **0.850** |

### 5.5 解釈(T8bの判定)

**単独チャネルの差し替え(proprio_swapまたはimg_swapのみ)は、いずれの層でも
プローブの予測を元(base)に留める方向に働く**(follows_source率はほぼ全て0.5未満、
深層ではimg_swap単独で0.12-0.27まで低下)。これは、proprio単独/画像単独の
「部分的な」条件付け差し替えは、モデルにとって一貫性のない(どちらの episode にも
完全には対応しない)入力になり、むしろ元の行動潜在に留まりやすいことを示唆する。

**しかし全条件付け(画像+proprio)を同時に差し替えると(all_swap)、深さに応じて
明確に単調増加する形でsourceへの追従が強まる**(Blk-9:0.68→Blk-13:0.67→
Blk-18:0.73→Blk-22:0.77→**Blk-27:0.85**)。これは、**深層のgripperデコードは
「画像+proprioが一貫した(自己整合的な)条件付けとして揃って差し替えられた場合」に、
条件付け由来の情報へ明確に追従する**という、レビューが要求した因果検証に
直接応える結果である。self-check精度(0.75-0.92)を踏まえると、この結果は
ノイズでは説明できない。

**訂正した結論**: T8(v2 §3.4)の「gripper 96-97%は条件付け経由で少なくとも
部分的に説明できる」という主張は、本テストにより**単独チャネルでは支持されない
が、画像+proprioの結合条件付けとしては支持される**、とより正確に述べ直す
必要がある。また、深さに応じた単調な追従率の増加は、Blk-18が自己注意サージ・
T8のproprio感度・J-bで示した「条件付けへの特異的な感度」と一貫しており、
**深層ほど条件付けの結合表現への依存が強まる**という描像を強化する。

**限界**: N=360(15 episodes)は元の確立されたプローブ(N=1108, 50 episodes)より
小さく、Blk-18/22のbaseline精度が20pp低い。§5.3で追加検証した通り、この精度差は
**サンプルサイズだけでは説明できない**(良いデータを同規模に縮約しても86%以上を
維持する)ことが確定しており、レイアウト・画像・言語条件付けの多様性も原因では
ないことを確認した。**真因は本セッションでは特定できておらず、未解決の限界**
として記録する。より大規模なpoolでの再現、および本テストのロールアウト自体の
成功率・行動品質の確認が今後の課題である。

## 8. 軽微な項目

### 8.1 pad検証の照合残差の表現訂正（レビュー §5 対応）

v2 §7.6は「`max|reconstruction-real_output|=4.89×10⁻⁴`（bf16丸め相当、T1/T2の合否基準
1e-4とほぼ同水準）」と記述していたが、これは不正確である。4.89e-4はT1/T2基準の1e-4の
**約4.9倍**であり、「ほぼ同水準」ではない。ただし、この規模の残差はbf16精度で
512キー(実トークン+パッド)×head_dim次元にわたる累積和(softmax(QK^T/√d)·V)の
丸め誤差として妥当な範囲であり、隠れマスクの存在を示唆するものではない
(隠れマスクがあれば、pad位置への寄与が体系的に0からズレるはずだが、実測では
全層で厳密に0.000000だった)。**訂正した記述**: 「4.89×10⁻⁴はT1/T2の合否基準(1e-4)の
約5倍だが、512キー×head_dimにわたるbf16累積和の丸め誤差として説明可能な水準であり、
隠れマスクの証拠にはならない」。

### 8.2 σ_data再較正の感度分析（レビュー §5 対応）

v2 §7.5は「§3.Aのヌルは実測std=0.443、EDM設計値は0.5」という不一致を記録しつつ、
感度は未計算としていた。`linear_gaussian_null()`の解析式を用い、σ_data=0.443と0.5で
schednorm正規化後のヌル値を比較した(`sigma_schedule=[80.0,42.3,21.0,9.6,4.0]`,
`D=T×D_act=32×7=224`, `k=3→4`遷移):

| σ_data | null(k=0→1) | null(k=3→4) | 実測/null (k=0→1) | 実測/null (k=3→4) |
|---|---|---|---|---|
| 0.443 (実測) | 0.0513 | 0.4845 | **1.29×**(超過) | **0.48×**(過小) |
| 0.5 (EDM設計値) | 0.0654 | 0.6156 | **1.01×**(超過ほぼ消滅) | **0.38×**(より過小) |

**結論**:
- §7.2(a)の中核結論「モデルは最終ステップ(k=3→4)で線形ガウス最適推定よりも小さい
  変化しか起こさない」は、σ_dataをEDM設計値0.5に再較正すると**むしろ強化される**
  (0.48×→0.38×)。この結論は頑健である。
- 一方、k=0→1で観測された「1.29倍の超過」という補助的な観察は、σ_data=0.5では
  **ほぼ消滅する**(1.01×、ヌルとの有意差なし)。この観察はσ_dataの較正に敏感であり、
  独立した主張として強調すべきではない(v2はこの点を主要な結論に含めていなかったため、
  実害はないが、今後この数値を引用する際は較正依存性に注意する必要がある)。

## 9. 統合結論

### 9.1 round 2からの主要な変更点

1. **T6「run間変動」説の撤回**(§2): round 2レビューが最も重視した「run変動が
   レポート全体の信頼性を脅かす」という懸念の主要な根拠(T6の+7〜21pp)は、
   実際には**同一runの中でのPCA前処理選択(標準化 vs 中心化)という単一の、
   ありふれた要因**で完全に説明できることが判明した。レビューの診断
   (「run変動」)自体は誤りだったが、レビューが要求した「厳密な要因分解」は
   完全に正しく、より単純で決定論的な真因の発見につながった。
2. **チェックポイント同一性の確定**(§1): 全ての解析が単一の同一ポリシー
   チェックポイントを使用していたことをHFキャッシュのblobハッシュで直接確認。
   run間変動の隠れた原因としてのチェックポイントdriftは排除された。
3. **PRのepisode数依存性は方向として正しかったが、`extended_step_effrank_jb.py`の
   低PRの真因は別にあった(発見・修正・再検証済み)**(§3, §4): 良いrunの実データを
   使ったepisode単位縮約は、PRが真にepisode(シーン)数に依存し、25epで既に
   元の値の95%程度(53/55.9)に収束することを確認した——ここまではround 2の説明を
   裏付ける。**しかし**、`extended_step_effrank_jb.py`系列のスクリプトで実際に
   episode数を25→50に倍増させても低いPR(2-4)のままであり、round 2の「episode数」
   という説明ではこの系列スクリプトの低PRを説明できないことが判明した。
   「キッチンレイアウトの多様性」「画像ピクセルの多様性」という2つの仮説を
   検証・否定した後、さらに追跡し**真因を特定**: `extended_step_effrank_jb.py`は
   全callで初期ノイズのseedを固定していた(良いrunは`seed=cfg.seed+ep_idx+t`で
   call毎に変化させていた)。シーンを一切変えずseedのみ変化させるクリーンな実験で、
   Blk-4/9/13のPRが2-4→50-54に完全復元することを実証した(§4.3)。スクリプトを
   修正し(`seed=cfg.seed+total_calls`)、2回の独立な再実行で崖→滑らかの結論
   (σ=21→4にわたる連続的な多段階減少)が正しい絶対値の上で再現されることを
   確認した(§4.5)。J-bは元々このバグの影響を受けていなかったことも確認した
   (§4.6)。
4. **T8bによる情報源テストの新規実施**(§5): 単独チャネル(proprioのみ/画像のみ)の
   差し替えではプローブは元(base)に留まるが、**画像+proprioを同時に差し替えると、
   深さに応じて単調にsourceへの追従が強まる**(Blk-27で85%)。これは
   レビューが要求した因果検証に直接応え、「条件付け由来」という説明を
   (単独チャネルではなく結合表現としてという限定付きで)支持する新たな
   直接証拠である。
5. **σ_data感度分析**(§8.2): commitment棄却の中核結論はσ_data再較正で
   むしろ強化される(0.48×→0.38×)ことを確認し、頑健性を追加で示した。

### 9.2 何が今も頑健に確定しているか

- ε_θ/D_θの誤ラベリング訂正、pad寄与ゼロの実証、d_proxyの除去、C2F表現の弱化
  (v2で確定、本レポートでの再検証により揺らいでいない)。
- 行動出力レベルのcommitment棄却(§3.A系)は、σ_data再較正でむしろ強化。
- Blk-18が複数の独立解析(自己注意・T8・T8b・J-bの形状)から一貫して指し示される
  という観察は、4つ目の独立証拠(T8b)の追加によりむしろ強化された
  (§7)。ただしmulti-seed確認は依然として未実施。
- 深層のgripperプローブ高精度は、「現在の生proprioの単純な通過」では説明
  **できない**(§5.3、新たな反証)一方、「画像+proprioの結合条件付け」の
  差し替えには深さに応じて明確に追従する(§5.4)——両者を合わせると、
  深層は**単純なパススルーではなく、条件付けの非自明な結合表現**を
  読み出していると解釈するのが最も証拠に忠実である。

### 9.3 何が新たに「未解決の限界」として記録されるべきか

- **T8bのbaseline probe精度(N=360, 15ep)は元の確立されたprobe(N=1108, 50ep)より
  Blk-18/22で20pp低く、この差は追加検証により「サンプルサイズの違い」では
  説明できないことが確定した**(§5.3: 良いデータを同規模に縮約した20回の
  再抽出は全て86%以上を維持し、T8bの74.7-77.5%には一度も届かなかった)。
  レイアウト・画像・言語条件付けの多様性も原因ではないことを確認済みだが、
  **真因は本セッションでは特定できておらず、正真正銘の未解決の限界**として
  記録する(§5.4)。
- Blk-18三角測量・プローブ層順位はmulti-seedでの再現確認が引き続き未実施
  (T6訂正により「run変動が全てを疑わしくする」という一般論的な懸念は
  弱まったが、複数独立実行を跨いだ主張であることに変わりはない)。
- **教訓として記録**: policy call毎に`get_action`へ渡す`seed`引数は、
  デノイジングの初期ノイズを直接制御する(`torch.Generator().manual_seed(seed)`)。
  複数callにわたる特徴量の多様性(PR等)を測定するスクリプトでは、
  **必ずcall毎に異なるseedを使うこと**を実装チェックリストに追加すべきである
  (`feature_analysis.py`の`seed=cfg.seed+ep_idx+t`が正しい参考実装)。
